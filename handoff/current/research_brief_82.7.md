## PART B -- EXTERNAL RESEARCH

### Q1. Authoritative guidance: credentials in URL query strings

**RFC 6750 (OAuth 2.0 Bearer Token Usage, IETF Standards Track)** is the sharpest
normative source. Section 2.3 "URI Query Parameter"
(https://www.rfc-editor.org/rfc/rfc6750, accessed 2026-08-04):

> "Because of the security weaknesses associated with the URI method (see Section 5),
> including the high likelihood that the URL containing the access token will be
> logged, it **SHOULD NOT be used** unless it is impossible to transport the access
> token in the 'Authorization' request header field or the HTTP request entity-body."

> "This method is included to document current use; its use is **not recommended**,
> due to its security deficiencies (see Section 5)."

Section 5.3:

> "Bearer tokens SHOULD NOT be passed in page URLs (for example, as query string
> parameters). Instead, bearer tokens SHOULD be passed in HTTP message headers or
> message bodies for which confidentiality measures are taken. Browsers, web servers,
> and other software **may not adequately secure URLs in the browser history, web
> server logs, and other data structures**."

Section 2.1, the positive requirement:

> "Clients SHOULD make authenticated requests with a bearer token using the
> 'Authorization' request header field with the 'Bearer' HTTP authorization scheme.
> Resource servers MUST support this method."

**Applicability caveat (stated honestly):** RFC 6750 governs OAuth *bearer tokens*,
not vendor API keys. A FRED/AlphaVantage/Finnhub key is not formally a bearer token.
But the stated *reason* -- "the high likelihood that the URL containing the access
token will be logged" -- is a property of the URL transport, not of the token format,
and it is exactly the failure being remediated. Cite RFC 6750 as governing rationale
by analogy, not as a literal compliance obligation.

**OWASP Logging Cheat Sheet**
(https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html, accessed
2026-08-04), section "Data to exclude", never-to-be-logged:

> "Access tokens" ... "Authentication passwords" ... "Database connection strings"
> ... "Encryption keys and other primary secrets"

prefixed by "Never log data unless it is legally sanctioned."

Its "Event collection" section gives the *placement* guidance:

> "Perform sanitization on all event data to prevent log injection attacks e.g.
> carriage return (CR), line feed (LF) and delimiter characters (and optionally to
> remove sensitive data)"

-- i.e. sanitize during **collection, in a centralized handler**, not per call site.

**CORRECTION to `log_redaction.py`'s own docstring:** the cheat sheet contains no
sentence reading "sanitize secrets at the logging layer, not at every call site"
(attributed to OWASP at `log_redaction.py:9-10`). The *substance* is supported by the
two quotes above, but the attributed quote is a paraphrase presented as a citation.
Worth correcting while the file is open. Also note the Logging Cheat Sheet does **not**
itself prohibit URLs in logs -- it lists entry-point URL as a legitimate event
attribute. The URL-specific prohibition comes from RFC 6750 and OWASP secure-code-review
guidance ("Credentials and secrets in URL parameters leak through browser history,
proxy logs, analytics, and Referer headers").

### Q2. Fix hierarchy + what the httpx maintainers actually say

Official httpx logging page (https://www.python-httpx.org/logging/, accessed
2026-08-04):

> "If you need to inspect the internal behaviour of `httpx`, you can use Python's
> standard logging to output information about the underlying network behaviour."

Two loggers -- "the high-level `httpx` logger, and the network-level `httpcore`
logger, which can be configured separately." The documented INFO line is **exactly
the shape that leaked**:

> `INFO [2024-09-28 17:27:41] httpx - HTTP Request: GET https://www.example.com "HTTP/1.1 200 OK"`

**There is NO official knob to disable or redact it.** The page documents only how to
*enable* and format logging. "Ask httpx to redact" is not an available option.

**Recommended hierarchy (strongest first):**

1. **Move the credential out of the URL into a header** -- eliminates the class.
   RFC 6750 2.3/5.3's own remedy. Availability is per-provider (Q5).
2. **Redact at the logging layer (handler-level filter)** -- the OWASP centralized-
   sanitization answer, and defence-in-depth that keeps working where (1) is
   impossible and for every future call site. **This repo already has it; it is just
   not installed everywhere** (A2).
3. **Silence the `httpx` logger (`setLevel(WARNING)`)** -- weakest, and it is an
   **availability/observability risk, not a security control**. It suppresses the
   *evidence*, not the secret; it is trivially undone by any future
   `basicConfig(level=DEBUG)`; and it does nothing for `httpcore`, for exception
   reprs embedding the URL, or for any other library that logs a URL. Belt-and-braces
   only -- never the fix.

(1) and (2) are **complements, not alternatives**: (1) removes today's 8 sites, (2) is
what makes the *next* one safe. A fix that does only (1) leaves the repo one
`f"...&api_key={k}"` away from a repeat -- and Alpha Vantage (Q5) makes (1) impossible
for 2 of the 8 sites regardless.

### Q3. Handler-level vs logger-level filters -- CONFIRMED against the primary source

Python official docs (https://docs.python.org/3/library/logging.html#filter-objects,
accessed 2026-08-04):

> "Note that filters attached to handlers are consulted before an event is emitted by
> the handler, whereas filters attached to loggers are consulted whenever an event is
> logged (using `debug()`, `info()`, etc.), before sending an event to handlers."

The decisive sentence:

> "This means that events which have been generated by **descendant loggers will not
> be filtered by a logger's filter setting**, unless the filter has also been applied
> to those descendant loggers."

`Handler.filter()`:

> "Apply this handler's filters to the record and return `True` if the record is to be
> processed. The filters are consulted in turn, until one of them returns a false
> value."

On in-place mutation:

> "Filters can either modify log records in-place or return a completely different
> record instance which will replace the original log record in any future processing
> of the event."

**Verdict: `log_redaction.py`'s architectural claim (`:5-9`) is CORRECT and is now
backed by the primary source.** A root-*logger* filter would NOT catch `httpx`'s
records; the root-*handler* filter does. The design is right -- only its reachability
is broken.

**Forward-looking subtlety:** Python 3.12 added -- "You can now return a `LogRecord`
instance from filters to replace the log record rather than modifying it in place.
This allows filters attached to a `Handler` to modify the log record before it is
emitted, **without having side effects on other handlers**." Our filter mutates in
place (`log_redaction.py:43-44`), so with multiple handlers the redaction *propagates*
to them. For a redaction filter that side effect is **fail-SAFE**. Do not
"modernise" it to the 3.12 return-a-record form -- that would make redaction
handler-local and could un-redact a second handler.

### Q5. Per-provider: is header auth even available?

| Provider | Header auth? | Evidence | Verdict |
|---|---|---|---|
| **FRED** | **YES -- API Version 2**, `Authorization: Bearer <key>` | FRED launched API v2 on **2025-11-04**; in v2 "an API key must be specified in the request header in the following way: `Authorization: Bearer ...`". Official doc `https://fred.stlouisfed.org/docs/api/fred/v2/api_key.html` **403s to automated fetch** (see Limitations); corroborated by the St. Louis Fed press announcement ("FRED Launches New Version of API") and the `fred/v2/*` endpoint doc index. | Strongest fix available, **but it is a v2 endpoint migration** (new `/fred/v2/...` paths), not a header swap. Scope it as a real change with its own verification. |
| **Alpha Vantage** | **NO** | https://www.alphavantage.co/documentation/ (read in full, accessed 2026-08-04): key supplied "exclusively through the `apikey` query parameter... no documented method to pass the key via HTTP headers"; every example is `&apikey=demo`. | **Header fix IMPOSSIBLE.** Redaction is the only control for sites #5/#6. |
| **Finnhub** | **YES** -- `X-Finnhub-Token` | Finnhub accepts `?token=` **or** the `X-Finnhub-Token` request header. GitHub `finnhubio/Finnhub-API#301` (read in full): title *"API token should be accepted as a header, not a query parameter."*; reporter TJNII (2020-06-24): *"This is a security concern as passing the token as a query parameter makes it part of the URL, which is frequently logged by application level logging but also commonly logged by proxies."* No maintainer reply in-thread; the header was nonetheless implemented. | Cheap, high-value fix for sites #7/#8. |

**This is the single most decision-relevant external result: Alpha Vantage CANNOT do
header auth, so a header-only fix is structurally incomplete. The redaction-
reachability fix (A2) is the load-bearing one.**

**OWASP has a dedicated vulnerability entry for exactly this**
(https://owasp.org/www-community/vulnerabilities/Information_exposure_through_query_strings_in_url,
accessed 2026-08-04):

> "Information exposure through query strings in URL is when sensitive data is passed
> to parameters in the URL."

Exposure locations listed: **"Referer Header", "Web Logs", "Shared Systems", "Browser
History", "Browser Cache", "Shoulder Surfing"** -- and, without encryption,
"Man-in-the-Middle". Detectability is rated **"Difficult"** and prevalence
**"Common"**, which matches this incident precisely (it went unnoticed until it
appeared on an operator console). Critically:

> "Simply using HTTPS does not resolve this vulnerability."

That sentence pre-empts the most likely objection to this step ("but the FRED call is
TLS").

### Q4. Making a logging filter reach CLI/script entry points -- options and trade-offs

Primary source (Python logging cookbook,
https://docs.python.org/3/howto/logging-cookbook.html, accessed 2026-08-04):

- Filters may legitimately mutate records: *"`Filter` instances are allowed to modify
  the `LogRecords` passed to them, including adding additional attributes..."*
  ("Using Filters to impart contextual information").
- Under **"Patterns to avoid"**: *"Adding handlers other than `NullHandler` to a
  logger in a library"* -- so the redaction plumbing belongs in an **application
  entry-point bootstrap**, NOT inside `log_redaction.py`'s import side effects and
  NOT inside the ingestion modules.
- `dictConfig()` is the documented centralized mechanism: the cookbook's
  "An example dictionary-based configuration" recipe passes a dict to `dictConfig()`
  "to put the configuration into effect".

Practitioner prior art (relaxdiego, "Hiding Sensitive Data from Logs with Python",
2014 -- the canonical year-less hit,
https://relaxdiego.com/2014/07/logging-in-python.html, accessed 2026-08-04) gives the
two shapes and the trade-off. Filter-in-YAML: *"Notice how `filters` is an array.
Therefore we can add as many filters as we need here."* Formatter-wrapping,
programmatic:

```python
for h in logging.root.handlers:
    h.setFormatter(RedactingFormatter(h.formatter, patterns=[...]))
```

with the notable justification that programmatic attachment *"is actually good in a
way, as it will always get applied irrespective of what the user configures."*
**That is directly applicable here** -- it is an argument for a programmatic
`install_redaction()` over a config-file-only approach, because 40 files in this repo
each call `basicConfig()` with their own config.

| Option | How | Pros | Cons | Fit here |
|---|---|---|---|---|
| **A. Shared bootstrap function**, e.g. `backend/services/observability/log_redaction.py::install_secret_redaction()` that idempotently adds the filter to **every existing root handler** and is called from each entry point | one import + one call per entry point | explicit, testable, no import magic, idempotent, avoids the `setup_logging` destructive re-init (A6) | must be added to N entry points; a new script can forget it | **RECOMMENDED PRIMARY** |
| **B. `logging.config.dictConfig`** | central dict | official "non-trivial application" answer | requires *replacing* 40 `basicConfig()` calls -- huge blast radius for a security fix | later cleanup, not this step |
| **C. `sitecustomize.py` / `.pth` import hook** | auto-applies to every interpreter start | zero per-script edits; catches scripts nobody thought of | **invisible action-at-a-distance**, environment-dependent (not installed in all venvs), breaks under `-S`, hostile to debugging; ordering vs `basicConfig()` is fragile | reject as primary; note as defence-in-depth only |
| **D. Attach at import time in `log_redaction.py`** | module side effect | automatic for anything importing it | violates the cookbook's library-shouldn't-configure rule; import order dependent | reject |
| **E. Monkeypatch/silence `httpx` logger** | `setLevel(WARNING)` | one line | availability risk, not a security control (Q2) | reject as primary |

**Critical ordering constraint** (surfaced by the Prefect-filter practitioner write-up
and consistent with A2): *sanitize as early as possible -- if a secret is logged
before the filter is attached, the damage is already done.* So the bootstrap call must
precede the first HTTP call, and must run **after** whatever `basicConfig()` the
script does (otherwise `basicConfig` is a no-op-if-handlers-exist and ordering gets
subtle). An `install_*` that iterates `logging.root.handlers` and adds the filter to
each, and is safe to call repeatedly, handles both orders if called last.
